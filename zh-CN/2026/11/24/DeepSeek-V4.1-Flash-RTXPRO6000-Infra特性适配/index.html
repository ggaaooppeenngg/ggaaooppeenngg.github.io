在 RTX PRO 6000 上跑通 DeepSeek-V4.1-Flash：Infra 特性逐项适配与 CSA2 的完整支持

发表于 2026-11-24 更新于 2026-11-25 分类于 技术

DeepSeek-V4.1-Flash 的官方推理栈是按 H100 到 GB300 和 MI355X 搭的：vLLM 0.30 到 0.32 三个正式版本在 RTX PRO 6000 上连模型都起不来，栈里的 DeepSelect 只编 sm_100a 和 sm_103a，DeepSeek 自己的推理引擎 DeepInfer 只支持 SM100 和昇腾 950。本文记录在 4 张 RTX PRO 6000 上把 V4.1 的 Infra 特性逐项跑通的经过：先让基座模型启动，再把 FP4 KV、MXFP4 Engram、KV 卸载、DSpark 逐个打通，最后把 CSA2 补到完整——包括 Reindex 层只给候选块打分这条被上游硬性排除的路径。 结果是模型的 9 项特性全部跑通；吞吐和引擎特性的状态见最后三节。数字多数来自 84 GB 的 RTX 6000D 实测。

1. 官方栈与 SM120 的距离

V4.1 的推理栈由几个分工明确的组件拼成。先看每一个在 SM120 上的状态：

组件 作用 官方支持的硬件 SM120 上的状态
DeepInfer DeepSeek 自己的推理框架，相当于 DeepSeek 版的 vLLM SM100、昇腾 950 ❌ 非 SM100 直接报错
vLLM 引擎与接线 H100 ~ GB300、MI355X ⚠️ 0.30–0.32 起不来；稀疏 indexer 的自动开启只认 SM100
DeepGEMM MoE GEMM、MQA logits、融合大内核 SM90、SM100 ⚠️ 12 族内核里有 8 族，缺整个 MegaMoE 家族和 mega_mhc 主体
DeepSelect indexer 与采样的 top-k sm_100a、sm_103a ❌ 没有 SM120 的编译目标
FlashInfer 稀疏 MLA 注意力、量化 GEMM 含 SM120 ✅ 0.7.1rc5 起带 V4.1 的 sm120 内核配置

DeepInfer 是 DeepSeek 生产服务在用的那套引擎，它的 README 给了一份特性清单，这份清单就是本文所说的「V4.1 的 Infra 特性」的范围：优化内核与模型、采样运行时；Attention DP 与均衡的上下文并行；MoE 的 EP 与 EPLB；DSpark 与按置信度调度的验证；SWA bounded replay；异步调度；batch-invariant 推理；确定性采样；结构化输出。第 5 节的矩阵逐项对照它。

距离的根源在硬件。SM120 没有 cluster 和 multicast，没有 UMMA、TMEM、UTCCP，DeepGEMM 在它上面只能走 mma.sync 加 split-K；也没有 FP32 scale 的 MMA 路径，scale 必须是 UE8M0（2 的幂）。上游针对 GB300 的 latency_specialized decode 路径同样用不上：它的 mHC all-reduce 要求 NVLink multicast，4 张卡之间只有 PCIe。

所以能借的只有 FlashInfer，其余的要么补、要么自己写。工作分三层：让模型启动（第 2 节），把特性逐个跑通（第 3 节），把 CSA2 补完整（第 4 节）。

一句话总结：官方栈的四件套里，SM120 只有 FlashInfer 能直接用；DeepSelect 和 DeepInfer 关门，DeepGEMM 缺三分之一。

2. 先让基座模型启动

2.1 KV 几何补丁链

V4.1 的压缩 KV 层带一个逐层的压缩比：0 是纯滑窗层，1 是全长压缩缓存，2 是二比一压缩，这份 checkpoint 的序列是 [0,0,2,2,...,2,1,1,1,1,1]。vLLM 的块大小以 token 计，一个压缩层一页里有 block_size // compress_ratio 个 KV 条目。

64 来自内核。 FlashInfer 的 SM120 稀疏 MLA 调度器把页大小写死成 64（_PAGE_BLOCK_SIZE = 64），decode 内核只在 64 个条目一页上做了实例化；Hopper 一族也是这个布局，128 条目的页是 SM100 专属。于是在 SM120 上没有一个全局块大小能同时满足两种压缩比：全局 64 token，二比一压缩层一页只剩 32 个条目，报 page_block_size=32 is unsupported；全局 128 token，SM120 的内核集里又没有 128 的实例化。上游 issue #59203 记录的就是这个死结。

补丁的思路是逐层声明，让每个压缩层的一页都恰好 64 个条目：block_size = 64 * max(1, compress_ratio)。压缩比 1 的层每块 64 token，压缩比 2 的层每块 128 token，压缩比 0 的纯滑窗层按 64 处理。落到 4 个文件上：

  • attention.py 里两处 KV spec 的块大小按上式逐层计算，滑窗的块大小从 32 改成 64；
  • 两个注意力后端的 get_supported_kernel_block_sizes 对 SM120 返回 [64, 128]，让 KV 管理器按层各取所需。

一个小坑：is_device_capability_family 的参数是 CUDA family 编号，SM120 要写 120，不是 12。

上游后来合入了修复（#60762）：indexer 后端、稀疏 MLA 后端和 FlashInfer 后端在 SM12x 上声明 64-token 的内核块，和 SM90 的分支对齐。它选的是统一 64 token 的方案，二比一压缩层一页 32 个条目，前提是 FlashInfer 不低于 0.7.1rc5，页大小改成了运行时参数。那个 PR 的验证矩阵里，统一 64 和「逐层 [64, 128] 加 64*max(1, cr)」两种变体都能启动并通过正确性检查。换到这个基线之后，块大小的补丁不用再手工打：fp8 c16 的输出吞吐和缓存命中率，都和 0.31.0 加补丁是同一档。

2.2 两个环境坑

FlashInfer 混装。 从 0.7.0.post1 直接升级到 0.7.1rc5 会留下元数据与文件不一致的脏状态：引擎启动成功，logits 却全是 NaN，输出全空，prefill 的第一次前向就已经坏了。唯一可靠的解法是卸载、删掉 site-packages/flashinfer、重装，再清掉 FlashInfer、vLLM、Triton 三处 JIT 缓存。

0.7.3 缺模板。 换到 FlashInfer 0.7.3 之后，NVFP4 触发新的 JIT 编译，报 mxfp8_gemm_cutlass_sm120.jinja not found。安装包里没有 csrc，把模板解包到 site-packages/flashinfer/data/csrc 才行，一共 4,707 个文件。

一句话总结：模型启动卡在两件事上，逐层的 KV 几何和一份干净的 FlashInfer；前者上游已经修好，后者每次换版本都要重来。

3. 特性逐个跑通

先在 nightly 上对 NVIDIA 的 NVFP4 版 checkpoint 做了一轮逐项 boot 实测。五个特性四个通过，唯一没有通过的 CSA2 留到第 4 节：

特性 结论 证据
checkpoint 加载（NVFP4 专家） ✅ 权重 75.26 GiB/rank，基座是 73.43
MXFP4 Engram ✅ 表卸载到主机内存，12.16 GiB/rank/表，FP8 的一半
FP4 KV cache（nvfp4_ds_mla） ✅ KV 池 738,225 tokens，fp8 KV 是 580,811（+27%）
KV cache 卸载 ✅ OffloadingConnector 与 CPUOffloadingSpec 正常创建
DSpark 投机解码 ✅ 余量极限 acceptance 54.5%；要 CTX 32768、SEQS 8 才装得下
CSA2 candidate sparse MQA logits ❌ 撞上 attention.hpp 里的架构断言

逐项说清楚「做了什么才通」：

FP4 KV。 0.31.0 把 nvfp4_ds_mla 门在 SM100。SM120 的出路是 FlashInfer 的 V41_FP4 压缩缓存内核：稀疏 MLA 注意力直接读 FP4 KV，读写都不经过 DeepGEMM。nightly 把这条路径接通之后，FP4 KV 成了默认项。

MXFP4 Engram。 上游 PR #61530 给 Engram 表加了 MXFP4 打包格式。当时它还没合并，移植的方式是整文件替换。两张表从每 rank 每张 23.60 GiB 降到 12.16 GiB，省的是主机内存。

KV 卸载。 原生的 OffloadingConnector 在 SM120 上直接可用。之后又移植了上游的 #65373（V4.1 的 CPU KV 在 TP rank 之间共享）。上限是 320 GiB，再往上会在区域初始化阶段静默退出，机制没有定位。

DSpark。 V4.1 取消了上一代的 MTP，DSpark 是模型唯一的投机解码方法，草稿权重随 checkpoint 一起发布：mtp.{0,1,2}.* 这组权重由 method=dspark 自动加载成 draft。机制一次就通，但读数经历了两层测量伪影才翻案：客户端按 SSE chunk 数 token，CUDA Graph 的捕获档位没覆盖投机步。修正之后的数字见第 5 节。

权重与算子。 路由专家出厂就是 MXFP4，走 DeepGEMM 的分组 GEMM（m_grouped_fp8_fp4_gemm_nt 的 masked 与 contiguous 两个变体）；线性层的 MXFP8 权重走 FlashInfer 的 CUTLASS；attention 投影另做了 NVFP4 W4A4 的转换。mHC 在 SM120 上走 TileLang 内核，在一份未命中 prefill 的 nsys 剖面里占 GPU 时间的 6.5%。

运行时。 SWA bounded replay 和异步调度都是上游默认开启，不需要额外处理——异步调度在不传 flag 时由 vLLM 自动决策，DSpark 在它的投机方法白名单里。多模态输入是缺口：--limit-mm-per-prompt '{"image":0}' 挡掉运行时的图像输入，避开 SM120 上的 vision 实例化问题。

五个特性里唯一没有通过的是 CSA2，下一节展开。

一句话总结：FP4 KV 靠 FlashInfer 的 SM120 内核，MXFP4 Engram 靠移植上游补丁，KV 卸载原生可用，DSpark 通了但要先修测量；到这一步，CSA2 的 consumer 层仍在全量打分再掩码。

4. CSA2 的完整支持

4.1 什么叫完整

CSA2 的索引器是一个两级漏斗，它是模型定义的一部分：索引器按两级候选训练，训练与推理用同一组约束，四个参数（候选源层、候选块数、块大小、top-k）都从 checkpoint 的 config 直通。Reindex 全网只有 4 层，都在解码器，每 4 层一个；带 indexer 权重的层一共 8 层，分两种角色，其余 30 个压缩层不带 indexer：

「完整」指的是 consumer 层真的只算这 16,384 个位置，索引打分的开销从 O(ctx) 降到 O(1)。上游的默认实现不是这样：它对整段上下文打分，再按候选块掩码。语义没有错，算力没有省。真正的算力跳过是 indexer_sparse_logits 开关背后的路径，它是 opt-in，自动开启只认 SM100；在 SM120 上不显式传 flag，这个开关恒为关闭。

4.2 三道门

把这条路径在 SM120 上接通，要过三道门：

环节 上游在 SM120 上的状态 做了什么
打分内核（只给候选块算 MQA logits） DeepGEMM 的 sparse MQA 内核只对 SM100 实例化，断言编在预编译的 .so 里 先自研 Triton 内核，再接上 DeepGEMM 开发分支里的 SM120 内核
top-k 选择 DeepSelect 只编 sm_100a 和 sm_103a torch.topk 加上与架构无关的候选展开和 remap
引擎接线 SparseMQAIndexer 要求 family(100)、DeepGEMM sparse MQA、DeepSelect 三者同时满足 放行 SM120，再做一轮实现审查

报错原文很直白：sm_120 (consumer Blackwell) ... not supported。它不是配置问题，是内核没有为这个架构实例化。

4.3 第一阶段：自研 Triton 路径

断言守护的是 SM100 才有的 tcgen05 指令，二进制补丁跳不过去，只能自己写。数学不复杂：逐头点积、relu、加权求和，但读的是引擎真实的 indexer k-cache——分段式的物理页布局，fp8 的值和 scale 分开放。这条路上连修四层 bug 才通关：把分段页读成交错布局、Qbar 折叠破坏了逐头 relu、fp8 字节被当成整数读、int32 页地址溢出。最后一层最隐蔽：页号超过 28,244 就溢出，修复只有两行。

数值验收是在 65K 真流量上做的：max_rel 0.39%，相关系数 0.999991，top-512 与正确语义的重合度 1.000。细节见《SM120 上的 candidate sparse MQA：四层 bug 和一个 int32 溢出》。

4.4 第二阶段：C++ 路线

DeepGEMM 的开发分支里其实有 SM120 的 sparse MQA 内核，契约是 FP8 的 Q 乘 MXFP4 的 K——这个混合精度是 SM120 独有的，SM100 反而不支持。接进来要改四处数值：Q 的 scale 被硬编码成单位值（GSM8K 只有 7%）、metadata 内核的对齐断言、top-k 选到 padding 里的垃圾槽、decode-dense 旁路的格式兼容。修完 GSM8K 300 题 97.33%。

之后又是两处崩溃，抓到的内核都不是真凶：一处是跨分区去重的归并越界，一处是 CUDA Graph 捕获时固化了 metadata 指针、排水时读到已回收的地址。两处都修在 DeepGEMM 的 C++ 层。

到这一步，SM120 上的 DeepGEMM 是 12 族内核里的 8 族：GEMM、einsum、MQA logits 的三段（dense、paged、sparse）都在，缺的是整个 MegaMoE 家族和 mega_mhc 的融合主体。

4.5 第三阶段：实现审查

能跑不等于对。之后对这条路径做了一轮实现审查，结论是两级候选的骨架完整且自洽——跨层共享、mask-before-topk、行对齐、CUDA Graph 下无同步，都逐一验证过。但 SM120 路径上审出了两个会直接破坏服务的问题：

多请求合包的 prefill 错位。 一个 chunk 里打包多个请求时，请求的 KV 在 workspace 里从第 ks 行开始，ks 是它前面所有请求的压缩长度之和，不一定是 8 的倍数。打分内核的窗口少了 ks % 8 这一项：

之前的数值验收大概率是在单请求、起点对齐的 dump 上做的，恰好掩盖了它。

与 MTP 同开必崩。 原生 next_n 等于 2 时，序列长度是每请求多行的布局，而 metadata builder 按每请求一行去展开，第一个投机步就报错。

修复落在 4 个文件里，另加一个离线测试：合成两个请求的合包 chunk，第二个请求 ks 取 13，和 torch 参照逐位对照。同一路径上还修了 6 处，其中一处和 A800 上的去同步是同一个问题——repeat_interleave 没带 output_size，每个 MTP decode 步多一次 GPU 到 CPU 的同步。其余是 pipeline 并行下候选池的孤儿读写、启动期校验、环境变量布尔解析的归一。

测试在机器上全部通过。C++ 路线处理的是同一件事：DeepGEMM 的调度内核里有按 si*8 + ks%8 寻址的非对齐模式，vLLM 这一侧要把请求起点的真实 ks 传下去并启用它。

4.6 状态

到这一步，分层稀疏索引器在 SM120 上有了完整的实现：4 个 consumer 层共享同一份候选展开结果，探针计数打分 50,864 次、展开 12,716 次，正好 1/4。收益那一侧还没有干净的结论：第 5 节里 Reindex 候选打分的数字都是和 DSpark 同开对 dense，投机解码的贡献混在里面；默认配置下走的仍是全量打分再掩码的等价路径。

一句话总结：CSA2 的完整支持分三步——自己写出打分内核、接上 DeepGEMM 的 SM120 实现、再用一轮审查把「能跑」变成「对」；SM120 上的 CSA2 从「语义等价」走到了「算力真的被跳过」。

5. 全部跑起来之后的吞吐

模型特性全部打开之后能跑到什么程度，分三层看。

单流。 DSpark 开、草稿深度 5：512 输入的单流 decode 是不开时的 3.5 倍（+249%），65K 输入约 5 倍（+398%）；acceptance 77.5%。

并发回放。 cc-traces（真实会话的请求 trace）的 39 个会话、600 s 窗，数字是开启相对不开的整机输出变化：

对照（开对不开） c16 c48 c64
DSpark，草稿深度 5（底座 A） +9.2% +37.6% +42.4%
Reindex 候选打分与 DSpark 同开（底座 B） −9.7% +30.7% +10.9%

随机 IO。 65K 输入、8 并发、EOS 口径，Reindex 候选打分与 DSpark 同开对 dense：总 decode +144%，单流 decode +144%；prefill −5.5%。

三点读法：

  • 投机解码的收益随并发变化：单流是 3.5–5 倍，到 c48、c64 是 1.1–1.4 倍的整机吞吐。
  • Reindex 候选打分与 DSpark 同开的那一轮，c16 比 dense 低 9.7%：它的 KV 池小 12%，prefill 交了 5.5% 的税，低并发时这两项盖过了算力节省；到 c48 反超 30.7%。两行各在自己的底座内可比，不能跨行相减。
  • dense 对照栈不开投机解码，其余特性（FP4 KV、MXFP4 Engram、MXFP4 indexer）全开，KV 池 2,861,437 tokens。

一句话总结：特性全开之后，单流 decode 是 dense 的 3.5–5 倍，并发回放的整机输出在 c48 以上高 11%–42%；代价是 KV 池和 prefill 各让出 5%–12%。

6. 支持矩阵

先看模型特性。它们随 checkpoint 一起来，是模型定义的一部分，支持模型就必须支持它们：

Lightning Indexer k-cache ✅ fp8 与 mxfp4 都通

Engram（MXFP4 表） ✅ 移植上游 #61530
SWA bounded replay ✅ 上游默认开启

一句话总结：V4.1 的 9 项模型特性在 SM120 上全部跑通；引擎特性里异步调度、MoE 专家并行、KV 卸载已验证，5 项没有测过，关着的几项都是上游没有 SM120 实现的可选内核或输入通路。

总结

  1. 距离。 官方栈按 SM100 和 GB300 搭建：DeepSelect 只编 sm_100a 和 sm_103a，DeepSeek 自己的引擎 DeepInfer 只支持 SM100，DeepGEMM 在 SM120 上是 12 族内核里的 8 族。能直接借的只有 FlashInfer。
  2. 路径。 先用 4 个文件的补丁链让基座模型启动，再逐项跑通 FP4 KV、MXFP4 Engram、KV 卸载、DSpark，五特性 boot 实测定了四个。
  3. CSA2。 完整支持分三步：自研 Triton 打分内核（四层 bug）、接 DeepGEMM 的 SM120 实现（四处数值、两处崩溃）、实现审查（修掉两个会破坏服务的问题）。Reindex 层的打分范围从整段上下文降到 16,384 个候选位置。
  4. 吞吐。 特性全开之后，单流 decode 是 dense 的 3.5–5 倍；cc-traces 回放里 DSpark 让 c48、c64 的整机输出高 37.6% 和 42.4%；Reindex 候选打分与 DSpark 同开时，随机 IO 的总 decode 高 144%，prefill 低 5.5%。
  5. 现状。 模型的 9 项特性在 SM120 上全部跑通。引擎特性里异步调度和 MoE 专家并行已验证，5 项没有测过；关着的几项是上游没有 SM120 实现的可选内核或输入通路。Reindex 候选打分的收益尚待同轮对照证明。

可迁移的启示：在一块不在官方支持矩阵里的硬件上适配新模型，顺序是先让模型启动、再逐项打通特性、最后才做「完整」。 每一步的验收标准不一样——启动看能不能出 token，特性看 boot 实测，完整要看到算力真的被跳过，并且与全量结果逐位对得上。
