4×RTX 6000D 上的 DeepSeek-V4.1-Flash：KV 池从 9 万做到 286 万 tokens

发表于 2026-11-24 分类于 技术

把 DeepSeek-V4.1-Flash 部署到 4 张 RTX 6000D 上，第一次跑通时 KV 池只有 9 万 tokens；九天之后，同一个模型、同一组卡，池做到了 2,861,437 tokens。关键是：sm_120 不在官方支持矩阵里、卡间没有 NVLink、单卡显存比 RTX PRO 6000 少 12 GB——这三个错位决定了优化重心不在算力，而在显存容量：贴顶之前，KV 池每多 1 GiB 都能换成 prefix 命中率。 本文按一本显存账讲清每张卡的显存怎么分、权重侧和 KV 侧各压掉多少、调度参数怎么腾出余量、冷层怎么配、哪几条路走不通。除特别说明外，数字都是同一台 4×RTX 6000D 工作站的实测（TP4/EP4，vLLM nightly 加 sm_120 补丁），池容量取启动日志里的 KV cache size，命中率注明口径。

1. 三个错位：sm_120、PCIe 与 84 GB

模型的主体结构（CED、CSA2、FP4 主 KV、Engram）在 DeepSeek-V4.1-Flash 架构解析 里已经讲过，这里只列和显存有关的几个事实：552B 骨干；路由专家出厂就是 MXFP4，磁盘上打包后 271.8 GB；Engram 是挂在第 1、14 层的两张 embedding 表，FP8 时约 189 GiB。把这样的模型放到 4 张 RTX 6000D 上，有三个错位。

错位一：sm_120 不在支持矩阵里。 vLLM 0.30 到 0.32 的正式版本在 sm_120 上都起不来：FlashMLA 的 sparse 路径只认 sm90，DeepGEMM 的 sparse MQA 打分和 DeepSelect 只认 sm100 家族，官方 recipe 覆盖的是 H100 到 GB300 和 MI355X。能跑起来靠的是 nightly 加一组 sm_120 补丁（按层改 KV 几何、放开 KV 块尺寸），本文所有数字都建立在这个前提上。

错位二：卡间没有 NVLink。 4 张卡之间只有 PCIe Gen5：NCCL AllReduce 的 busbw 实测 24.3 GB/s，一台 NVLink 机器上的同项测试是 153.9 GB/s，相差 6.3 倍。单卡 FP8 GEMM 能跑到 287 TFLOPS，是 bf16 的 2 倍，算力并不缺，但多卡通信把这点优势抵掉了。TP4 就是这台机器的上限形态，优化重心只能压在显存容量（KV 池）和单步开销上。

错位三：显存比 RTX PRO 6000 少 12 GB。 单卡 84 GB，权重装进去之后留给 KV 的余量非常薄。最极端的例子是 NVIDIA 的 NVFP4 整包 checkpoint：权重 75.26 GiB/rank，gpu-memory-utilization 取 0.95 时 KV 只剩 1.36 GiB，warmup 阶段一次 882 MB 的分配失败就是 OOM。

一句话总结：算力不缺、互联受限、显存紧张——这台机器上值得做的优化，是每一个 GiB 都要算清楚。

2. 显存账本：每张卡的显存怎么分

vLLM 启动时给 KV 池留多少显存，可以写成一个记账式子：

Npool=U⋅M−W−Apeak−GbN_{\text{pool}} = \frac{U \cdot M - W - A_{\text{peak}} - G}{b} Npool​=bU⋅M−W−Apeak​−G​

其中 UUU 是 gpu-memory-utilization，MMM 是单卡显存总量，WWW 是权重，ApeakA_{\text{peak}}Apeak​ 是 profile 阶段测到的最大激活占用，GGG 是 CUDA graph 占用，bbb 是每个 token 的 KV 开销。后面的每一节都在动这个式子里的某一项。

两个读法。第一，权重侧几乎没有再压的空间：路由专家一项就占 GPU 常驻权重的约 95%，而且出厂就是 4-bit；能动的只有零头（attention 投影、lm_head 这类）和 KV 的格式。第二，换算率是固定的：在这台机器上每 rank 省出 1 GiB 显存约等于 50.5 万 tokens，对 2.86M 的池来说是 17.6%。整池折算下来每个 token 约 2.1 KB，远大于主 KV 记录的 288 B——池里除了压缩 KV，还有滑窗 record（仍是 MXFP8）和 indexer cache，三部分一起才是池的大小。

一句话总结：权重约 70 GiB、KV 池 5.67 GiB，每省出 1 GiB 多约 50 万 tokens——后面所有的收益都按这个换算率折算。

3. 权重侧：两张 Engram 表和两个 attention 投影

3.1 MXFP4 Engram：主机内存减半

Engram 的两张表（第 1、14 层）不占显存，靠 --engram-config '{"cpu_offload":true}' 放在 pinned 的主机内存里，GPU 经 UVA 直接读取。基座 checkpoint 里是 FP8，每 rank 每张表 23.60 GiB；换成 MXFP4 之后是 12.16 GiB，主机内存正好减半。磁盘上两张表的体积从约 189 GiB 降到约 97 GiB。

格式本身不复杂：E2M1 两个值挤一个字节，每 32 个元素一个 UE8M0 scale。表不是自己量化的，而是把 NVIDIA 在它的 NVFP4 checkpoint 里校准好的 MXFP4 表原样移植过来（引擎侧是上游 PR #61530 的移植，只改 engram.py 一个文件）。

移植时踩了一个值得记下的坑。第一次验证，相对误差（rel-L2）是 143%，远大于预期的 12%。问题不在数据也不在内核，在验证脚本：它把一个字节拆成低 nibble 和高 nibble 之后，按「前一半低、后一半高」拼回去，而实际排布是交错的——偶数列在低 nibble，奇数列在高 nibble。

还有一处真实差异：两边的 scale 对不上，NVIDIA 的和自己推导的相差 6 或 7（UE8M0 的 scale 是 2 的幂，差的就是指数）。这是 NVIDIA 为 E2M1 的量程重新推导了 scale——FP8 组内 amax 约 288-448，要除以 64 或 128 才落进 E2M1 的上限 6。所以移植时 embed.scale 必须跟表一起搬，不能沿用自己按 amax 推导的那份。

修正之后行范数的相关性是 0.9968。质量门是 GSM8K 300 题 5-shot（thinking 关）：表面 97.67%，其中 4 题是评测脚本解析千分位逗号造成的误判，实际错 3 题，99.0%。吞吐与基座统计持平：65536×c8 下 prefill 14,228.8 vs 14,133 tok/s，聚合 decode（全部请求合计）289.4 vs 287.6 tok/s，单请求 decode 36.38 vs 36.1 tok/s。

这项优化对 GPU 池没有直接贡献——FP8 表本来就在主机上。它的价值在主机侧：省出来的内存可以分给 KV 冷层，上线的同时冷层从 256 GiB 提到了 320 GiB。

一句话总结：Engram 转 MXFP4 省的是主机内存（每 rank 每张表 23.60 → 12.16 GiB），不省显存；移植量化表时 scale 必须随表一起搬，验证脚本要先核对 nibble 排布。

3.2 ATTN4：wq_b / wo_b 的 NVFP4 W4A4

attention 的投影在基座里全是 FP8 W8A8。这里只转了两个：wq_b 和 wo_b，40 层共 80 个张量，离线用 RTN（round-to-nearest，就近取整）转成 NVFP4 W4A4——权重是 E2M1 加每 16 个元素一个 E4M3 scale，激活在运行时逐批量化。选这两个的理由很直接：它们是投影里最大的两个 GEMM，每层每 token 各约 84M FLOPs。wo_a 没转，因为它的自定义 kernel 直接读 FP8 + UE8M0 的原始字节；wq_a 和 wkv 很小，留在 FP8。

激活是动态量化，所以 checkpoint 里的 input_scale 只是占位，整个转换不需要校准数据。

池多出的 250,459 tokens 折合每 rank 约 0.5 GiB，就是这两个投影省下的显存。收益的来源是两头：权重字节减半，decode 时每步要读的投影权重和反量化开销都跟着降；省出的显存全部进了 KV 池。同一份权重放到另一台 4×RTX PRO 6000 96GB 上，池从 4,504,663 涨到 4,645,418（+3.1%）。

一句话总结：把 wq_b / wo_b 两个投影从 FP8 换成 NVFP4 W4A4，不需要校准数据，decode +9.7%、KV 池 +11.2%。

4. KV 侧：主 KV 换 FP4，indexer 换 MXFP4

4.1 主 KV：fp8_ds_mla 到 nvfp4_ds_mla

主 KV 的每 token 开销走过两个格式。fp8 的 V4.1 记录是 528 B：512 维全部按 fp8 e4m3 存，RoPE 那 64 维也量化，再加 16 个 UE8M0 scale（每 32 维一个）。FP4 的 nvfp4_ds_mla 是 288 B：512 个 E2M1 值两个挤一个字节共 256 B，加 32 个 E4M3 scale（每 16 维一个）。

这个 528 B 要和 DeepSeek-V4.1-Flash 架构解析 里的 584 B/token 区分开。584 B（448 B NoPE + 128 B RoPE + 8 B scale）是 V4 的记录布局：NoPE 用 fp8、RoPE 保持 bf16、每 64 维一个 scale。V4.1 的记录把 RoPE 也量化了，vLLM 在 SM100 和 SM120 上写进缓存的是 528 B 的 V4.1 记录，其它架构仍然写 584 B 的 V4 记录。

fp8 这一步先走。上游 PR #59846 里让 sm_120 写 V4.1 528 B 记录的那部分先移植到 0.31.0，池从 588,999 涨到 638,685（+8.4%）。FP4 这一步在 0.31.0 上到不了：planner 报 no decode instantiation，0.31.0 的 nvfp4 是 V3.2 的几何、只支持 sm100。要换到 nightly，由 FlashInfer 的 sm120 sparse MLA kernel 直接读 FP4 KV，读写都不经过 DeepGEMM。

FP4 的池增益有一组单变量对照，但不是在生产配置上测的，而是在 NVIDIA 的 NVFP4 整包 checkpoint 上（KV 余量太薄，只能 --enforce-eager、MNBT 2048、SEQS 16）：只改 --kv-cache-dtype，池从 580,811 涨到 738,225，+27%。记录从 528 B 降到 288 B，少了 45%，整池却只有 +27%——池里还有滑窗 record 和 indexer cache，它们没有跟着变小。回到基座 checkpoint 和生产配置之后，池是 2,030,756 tokens。

4.2 indexer k-cache：132 B 到 68 B

Lightning Indexer 只缓存 K、不缓存 V：每个 token 一条 128 维的 index key（32 个 index 头共用），query 对它做 q·k 打分。FP8 版每 token 132 B（128 B 的 K 值加 4 B scale），MXFP4 版是 68 B（64 B 打包的 E2M1 加 4 B UE8M0），每 token 省 64 B。

5. 池最大化旋钮：SEQS、MNBT、CGS、MEMFRAC、CTX

第 2 节的式子里，WWW 基本固定，ApeakA_{\text{peak}}Apeak​ 和 GGG 由启动参数决定，UUU 决定预算总量。逐个说。

MNBT（--max-num-batched-tokens）是一个调度步最多处理多少 token，也决定 prefill 分块的大小，所以 ApeakA_{\text{peak}}Apeak​ 基本正比于它。 这就是上下文 262,144 时 MNBT 开不大的原因：激活峰值把 KV 预算挤到低于上下文上限，而 vLLM 要求 KV 池至少装得下一条完整长度的序列，启动校验直接报 ValueError；再大就在 profile 阶段 CUDA OOM。具体到数字：

  • 0.31.0 那一代（fp8 KV、无投机解码）：MNBT 8192 能跑；16384 时 KV 池被压到低于 262,144；32768 是 CUDA OOM。
  • 加上 candidate sparse 的缓冲和投机解码之后，8192 也装不下了：autotune 的 dummy run 在余量上 OOM，降到 4096 之后池才从 3.38 GiB 回到 4.29 GiB。
  • 投机引擎上 MNBT 最敏感：从 4096 降到 2048，池从 961,859 涨到 2,396,462——4096 的 prefill 工作区预留占用了 78 万 tokens。但降太多会伤 prefill：MNBT 1024 时 prefill 只剩 7,477 tok/s，调回 4096 恢复到 13,812。

SEQS（--max-num-seqs）：fp8 时代从 64 降到 32 是池最大化的三项之一；池大了以后生产又用回 64。SEQS 从 8 提到 64，曾把 32 并发回放的 p50 时延从 194 s 压到 77.7 s。

CGS（--max-cudagraph-capture-size）：FULL 模式下是 CUDA graph 的捕获档位集合，档位越多图内存越大。图内存本身不大（一个投机引擎的 FULL 图，10 档，0.75 GiB），主要开销在 48、64 这种大 batch 的形状上。另一台 96GB 机器上捕获档位从 10 档加到 12 档，池从 4,645,418 降到 4,441,041（-4.4%）。

MEMFRAC：生产用 0.95。它是 KV 的总预算，不是 KV 的份额——gpu-memory-utilization 调低之后权重和激活照样要占，KV 反而更少。NVFP4 整包上从 0.95 降到 0.90，直接报 No available memory for cache blocks。

CTX：硬下限，池至少要装得下一条，生产用 262,144。开投机解码时 draft 的 KV 和 verify 缓冲都随 max_model_len 线性涨：早期一个投机解码加 candidate sparse 的配置里，上下文从 131,072 提到 262,144，池从约 218 万掉到约 94 万；底座换成 ATTN4 + MXFP4 indexer 之后，同样的 262,144 带着投机解码可以启动，池 1,422,296。

用 --kv-cache-memory 直接指定池的字节数时，不能信引擎的推荐值。 它绕过了 profile，没有安全网：一个稀疏 + 投机的引擎上，6.0 GiB 和 6.38 GiB 都能启动、随后 OOM，5.0 GiB 才稳（池 2,278,080）。原因是 profile 量不到运行期的瞬态分配，大约 0.7-0.8 GiB，而引擎推荐的「fully utilize」值正好没有留这部分。

旋钮 生产值 对池的影响 代价
MNBT 4096 越小池越大（投机引擎 4096 → 2048：+150%） 太小伤 prefill
SEQS 64 越小池略大 并发上限和排队时延
CGS 64 档位越多图内存越大（10 档 → 12 档：-4.4%） 档位外的 batch 走 eager
MEMFRAC 0.95 决定预算总量 调低反而 KV 更少
CTX 262,144 硬下限，投机缓冲随它线性涨 长上下文请求被拒

一句话总结：生产配方 CTX=262144 SEQS=64 MNBT=4096 CGS=64 MEMFRAC=0.95 是在「池尽量大」和「prefill 不被拖慢」之间量出来的点；MNBT 是其中对池影响最大的一个。

6. 冷层：KV CPU offload

--kv-offloading-backend native --kv-offloading-size 320 把 GPU 池里淘汰出去的前缀块换到主机内存。320 是 4 个 rank 合计的 GiB 数，每个 rank 80 GiB pinned 内存，启动时在 /dev/shm 里创建一个约 343.6 GB 的区域。冷层和 GPU 池共用同一个块管理器和同一张 prefix 哈希表，命中直接算 prefix cache 命中，不需要外部组件。

6.1 档位：320 是经验上限

冷层大小（GiB） 结果
256 早期的定版值
320 ✅ 生产值，MXFP4 Engram 上线后从 256 提上来
336 ❌ 失败 1 次，发生在 CUDA graph 捕获阶段，冷层还没创建，判断为无关的偶发
343 ❌ worker 在区域注册阶段被信号终止
384 ❌ 失败 2 次，都在区域初始化阶段
512 ❌ 四组对照全部负收益，/dev/shm 填充引发页缓存抖动

384 的现象值得写清楚。区域的创建分三步：mmap 创建 412.32 GB 成功，MADV_POPULATE_WRITE 物化（约 7 GB/s），最后 cudaHostRegister 注册 pin。两次失败都发生在这段初始化里，没有 traceback、没有 coredump，失败点还会漂移：一次是注册日志打出后卡了 120 s，被引擎主进程判定超时后 SIGKILL；一次是物化到 213 GB 时进程就没了。320 GiB 做对照，同一套流程一次通过。

五轮启动里排除掉的可能：

排除项 证据
内核 OOM oom_kill 计数为 0
cgroup 限额 memory.max 是 max
memlock 提到 unlimited 之后照旧；VmLck 恒为 0，CUDA 的 pin 不走 mlock 记账
systemd-oomd journal 干净
页缓存压力 posix_fadvise 清掉 381.4 GiB 权重页缓存之后照旧，MemAvailable 全程 628-836 GB
Xid dmesg 零记录

结论停在现象上：vLLM 0.33 nightly 在 40 层图模式下，CPUOffloadingSpec 的初始化路径和区域大小、时序相关地静默退出，机制没有定位。经验上限是 320。

6.2 冷层换来了多少命中

标准回放口径（3600 s 窗口）下，64 并发时 GPU 池的命中率只剩 13.9%（KV 池 97.5% 满载，前缀不断被挤出），未命中的部分有 93.8% 在冷层找到，综合命中率 94.74%；32 并发时 GPU 池命中 83.9%，综合 94.38%。代价在首 token 时间上：64 并发的 TTFT p50 是 37.9 s，32 并发是 0.698 s——冷层回迁发生在首 token 之前。64 并发这一档只能当批处理用。

6.3 读代码得到的三个事实

  • 冷读是一个 job、一次批量 DMA。 一个请求的全部 chunk 合成一个 job，走 cuMemcpyBatchAsync 一次驱动调用，不是逐页搬。
  • job 之间是严格 FIFO 的一条链。 stream.wait_event(last_event) 把 job 串起来，跨请求、跨读写；每个调度步先提交 store 再提交 load，满载时冷读排在持续的写入后面。
  • pin 失败只打一行 warning，然后退回 pageable 内存。 不会报错，也不容易察觉。

所以「冷层回迁只有 10 MB/s」这个数要这样读：它是 64 并发标准回放里用 TTFT 增量反推的等效值（66K token 对应约 21 s），包含排队和调度，不是传输带宽。在同一代引擎上单独测，32K 前缀的冷读 p50 是 0.188 s，和热读的 0.182 s 没有差别，CPU 到 GPU 的聚合带宽 54 GB/s。负载下的等效速度慢在 FIFO 排队，链路本身不慢。

vLLM 里还有另一套实现 SimpleCPUOffloadConnector，VLLM_USE_SIMPLE_KV_OFFLOAD=1 切换。同一个引擎上做了 A/B（两边池都是 1,328,571）：单发冷读打平（0.194 vs 0.188 s），并发冷读慢 18%（0.556 vs 0.472 s），并发热读慢 48%（0.579 vs 0.392 s）——它的 LRU 会把刚换入的块再淘汰出去。保持关闭。

6.4 适用条件

冷层要占物理内存：320 GiB 的区域，加上常驻的 pinned 内存和引擎自身，全套约 512 GB。另一台 4×RTX PRO 6000 96GB 的主机内存只有 503 GB：冷层设 320 GiB 时两次整机僵死，设 192 GiB 时在注册阶段被内核 OOM 终止，最后没有开冷层，靠 4.5M 的显存池维持命中率。

一句话总结：320 GiB 是 1 TB 内存机器上的经验上限，再往上会在区域注册阶段静默退出；它发挥作用的地方是满载时 GPU 池装不下的那部分命中。

7. 命中率的回报曲线：池多大才够

命中率看服务端指标 overall_usage_prompt_cache_read_pct，要开 --enable-prompt-tokens-details 才有。下面是同一代补丁、同一份 cc-traces 回放、冷缓存首轮的成对数字（p39、p72 是其中 39 个、72 个会话的两个子集，c16、c64 是并发）：

命中率随池单调，但只在同一代补丁、同一轮回放里可比——记录布局和回放调度都会让数字漂移，跨代的读数不能直接比。

什么时候贴顶：每个请求的前缀里有多少是之前出现过的，可以从 trace 直接算出来，这是命中率的理论上限；实测等于上限，再加池也不会涨。p39 的 16 并发实测 81.0% 对理论上限 81.0%，就是贴顶了，这份负载冷缓存的上限在 83% 左右。p72 的 64 并发在 699K 的池上只有 66.6%，是因为工作集远大于池，请求被反复挤出，p90 时延 373 s；池加到 2.03M 再配上冷层之后是 82.9%，p90 时延 175 s。

两件事容易误读。第一，回放第二轮起是热稳态：同一份会话集再放一遍，命中率会到 98% 以上（p39 链式热缓存，32 / 64 / 48 并发分别是 92.9% / 98.8% / 99.8%）。这是回放口径的产物，不是生产命中率。第二，并发比池更能决定命中率。另一台 96GB 机器上有一个极端例子：池 4.44M，96 并发实测命中 30.36%，理论上限 94.49%，TTFT p50 566 s——96 个 lane 的 unique 前缀工作集约 2700 万 tokens，远大于池。

标准口径（3600 s 窗口）下，这台机器上一个 2.4M 池加冷层的投机引擎，32 并发命中 94.38%（理论上限 94.9%），64 并发 94.74%。

一句话总结：池的回报以「贴顶」为界——实测命中率追平 trace 的理论上限之后，加池不再有用；越不过去的部分由并发和工作集决定，不是显存。

8. 启动：warmup autotune 的 1.5 h 到 4 min

换到 NVIDIA 的 NVFP4 整包 checkpoint 之后，引擎启动要 1.5 个小时，卡在 [AutoTuner]: Tuning mxfp8_gemm。原因是 FlashInfer 的 autotune 对每个 token bucket、每个形状逐个 profile；中途 OOM 崩溃的话缓存一个字节都不落盘，下次启动从头再来。

有意思的是，跳过某些算子的环境变量 VLLM_FLASHINFER_AUTOTUNE_SKIP_OPS 本来就存在，但对这条路不生效。flashinfer_sparse_mla_warmup.py 里的 _run_flashinfer_sparse_mla_decode_autotune 开了一个覆盖整个引擎的 tuning 上下文（flashinfer_autotune(True, cache=path) 包住整只 dummy run，所有可调优的 kernel 都进去选 tactic），但只传了 cache=，没传 skip_ops=；那个环境变量只被 kernel_warmup.py 里另一个入口读取。补丁就是让这里的四处上下文读同一个变量：

效果：mxfp8_gemm 改走启发式选择，attention 的调优保留（它有持久缓存），NVFP4 checkpoint 的启动从 1.5 h 降到 4 min。生产的环境变量值是 mxfp8_gemm,fp4_gemm。

一个附带结论：后来移植了上游把 autotune 峰值剔出 KV sizing 的改动（PR #66197），池一字不变，还是 2,861,437——主要开销已经 skip 掉，autotune 的峰值小于后面 4096 token 的 sizing 步，没有可回收的量。

一句话总结：一个早就存在的环境变量，因为 warmup 的另一条入口不读它而失效；补上四处读取，启动从 1.5 h 到 4 min。

9. 关闭的路与适用边界

9.1 对照表

9.2 关闭的路

LMCache。 外置 KV 层在 16 并发的回放上全面负收益：输出 184 vs 基线 253.6 tok/s，命中率 76.5% vs 87.2%。原因是这个并发下工作集 GPU 池本来就装得下，LMCache 只剩存储开销，外加 0.95 的利用率下 staging 缓冲反复分配失败（524 MiB 的块重试 12 次）。它适合的是工作集远大于池的过载区，不是这里。

prefix retention。 --prefix-cache-retention-interval 16384 是为 SWA 保留前缀检查点的参数，在 669K 的小池上命中率从 87.2% 掉到 78.6%，输出从 253.6 掉到 206.3 tok/s：检查点占块的开销大于命中收益。

内存互斥。 LMCache 的 L1、native 冷层、Engram 的 pinned 内存三者不能叠加：曾经 L1 512 GB 加冷层 512 GB 加 Engram 189 GB，超过 1007 GB 的物理内存，触发 global OOM，L1 的安全上限算出来约 610 GB。另外 expandable_segments 和 OffloadingConnector 互斥，配置校验阶段就会拒绝。

Engram 放 NVMe。 既然 Engram 在主机内存里，能不能再挪到 NVMe 腾内存？不能。vLLM 的 engram 磁盘卸载在配置校验里只支持 PLE 类模型，DSv4.1 直接报错，只有 cpu_offload 一条路。而且 cpu_offload 的意义是 pinned 内存供 GPU 经 UVA 零拷贝直读，decode 每步每层都要在 9600 万行里随机查找，NVMe 逐行随机读约 50-100 µs 一次，还在关键路径上；改用 mmap 加 page cache，热了以后页缓存照样占回内存。况且那台机器当时主机可用内存有 332 GB，并不缺这部分内存。

9.3 取舍表：什么情况下不该用

场景 是否有用 原因
请求的工作集本来就装得进 GPU 池 ❌ 冷层、LMCache 只剩存储开销
命中率已经等于 trace 的理论上限 ❌ 继续加池 贴顶之后不再涨
主机内存是 512 GB 这一级 ❌ 320 GiB 冷层 冷层全套约需 512 GB，超过物理内存
GPU 池只有几十万 tokens ❌ prefix retention 检查点占块的开销大于命中收益
需要保住 KV 池的投机引擎 ✅ MNBT 降到 2048 池 +150%
prefill 为主，又要保 KV 池 ⚠️ MNBT 低于 4096 池变大，prefill 变慢
主机内存宽裕 ✅ Engram 转 MXFP4 内存减半，质量无损

最后用两句交代剩余空间。权重侧基本到顶：路由专家出厂就是 4-bit，剩下的 BF16 零头（lm_head、embed、vision 塔）整机合计只有 3.68 GiB。按 checkpoint 的字节数估算，lm_head 转 FP8 加上 shared experts 转 MXFP4 还能把池从 2.86M 抬到约 3.02M（+5.6%），这两项还没有做。

一句话总结：关掉的那几条路有一个共同点——在工作集装得下的负载上，外置层只剩开销；在显存和主机内存都紧张的机器上，任何叠加都要先算总和。

总结

  1. 这台机器的约束是显存而不是算力：sm_120 要靠补丁，PCIe 限制了并行策略，单卡 84 GB 里权重占掉约 70 GiB。优化主线是把每一个 GiB 换成 KV 池，换算率是每 GiB 约 50 万 tokens。
  2. 九天里池从约 9 万到 2,861,437 tokens，其中能单独计量的几步：fp8 记录 +8.4%，调度参数 +70%，attention 投影转 NVFP4 +11.2%，indexer 转 MXFP4 +15.6%，FP4 主 KV 在单变量对照下 +27%。
  3. 冷层 320 GiB 补上了满载时 GPU 池的命中缺口，但上限由负载决定：实测追平 trace 的理论上限就是贴顶，越不过去的部分取决于并发和工作集。

可迁移的启示是：量化的收益要按「它占的是哪块内存」来记账。 Engram 转 MXFP4 对显存零贡献，却给冷层腾出了主机内存；indexer 转 MXFP4 的池增益里，每 token 省下的字节只解释了一小部分。账算对了，才知道下一步该动哪一项。
